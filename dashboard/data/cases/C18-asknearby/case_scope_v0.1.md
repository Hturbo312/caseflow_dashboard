## 2. 事件边界草案

### 2.1 建议纳入的核心过程

1. **平台技术框架与服务能力形成。**
   论文提出“感知—传输—平台—应用”四层架构，整合多源时空数据、时空知识图谱、地理邻近性增强的多模态 RAG 与垂域大语言模型。需要分别记录“技术组件”“平台声称具备的能力”和“在试运行中实际被使用的功能”，不得因架构图存在而推定全部功能已部署。
2. **北京大学深圳研究生院学术型社区试运行。**
   论文报告以 2024 年秋季入学新生为对象的 30 天试运行，涉及本地公共服务设施信息智能助手、自然语言问答、校园服务信息整合等；作者报告了渗透率、活跃用户峰值、活动半径、信息获取耗时和人工咨询需求变化等指标。上述行动可记为试运行已实施，效果数字暂记为“作者报告”。
3. **南头古城超高密度混合社区试运行。**
   论文报告平台在日均客流约 1.2 万人次、居住密度约 3.8 万人/km² 的南头古城开展试运行，涉及管理端网格化系统、居民互助、邻里在线社交、UGC 与导视更新等。论文未给出与高校场景相同的明确起止日期，试运行时间窗需在 G1/G2 补充或标为未确认。
4. **阶段性总结与效果报道。**
   论文对两个异构社区的试运行路径进行对比，报告平台在个体适应、信息供给、邻里互动和社区治理方面的作用。该总结属于作者基于试点数据的报道性结论，不能直接写成独立验证的因果结果。

### 2.3 建议排除或降为背景的内容

- **大语言模型、RAG、15 分钟生活圈的一般性文献综述**：仅作为技术情境，不纳入本案行动链。
- **论文提及的其他平台与项目**：如上海“美好生活掌中宝”、PlanGPT、AgentSociety 等，作为背景或对照，不并入 AskNearby 的实体与关系。
- **仅作为展望提出的功能**：如更大范围的多类型社区验证、长期跟踪、随机空间干预实验、社区监控视频与物联网融合等，未证明已实施的内容只能记为 `planned` 或 `unconfirmed`。
- **“方元问问”名称之外的“方元”组织、人物或商业主体**：论文只给出 APP 名称与英文名 `AskNearby`，未提供独立法人或运营公司信息；暂不将“方元”单独实体化。
- **同名或近名的其他“问问”产品**：如搜狗问问、通用问答社区，不纳入本案。
- **研究团队的其他项目与产品**：仅在与 AskNearby 的实际设计、部署或试点直接相关时纳入。

### 2.4 空间与对象范围

- 核心试点一：北京大学深圳研究生院及其学术型社区场景。
- 核心试点二：南头古城及其超高密度混合社区场景。
- 分析单元以“平台—社区试点—使用者/管理者行动”为主；不将“深圳全市”泛化为本案实施范围。
- 若后续材料证明平台已扩展到其他社区，应另设阶段或提请研究者调整边界，不先验并入。

## 3. 纳入 / 排除标准

### 3.1 材料纳入标准

1. 直接描述 AskNearby 的技术架构、平台功能、两处试点、使用者行动、管理端流程、数据治理或报告结果。
2. 提供可定位的时间、地点、参与者、功能使用、数量指标或效果口径。
3. 来源为论文原文、项目方/研究团队材料、平台页面、试点机构材料、独立报道或可核验的学术资料。
4. 网页与 PDF 材料须保留原始链接、页码/章节或存档快照时间。

### 3.2 材料排除标准

1. 只泛论大模型、RAG 或社区生活圈，未涉及 AskNearby 的内容。
2. 只有二手转述、无法回到原文或没有独立信息增益的内容。
3. 宣传性效果表述无法与试点数据、平台记录或独立材料区分者，只能记为“报道/观点”。
4. 与本案无直接关系的其他社区平台、研究项目或商业产品。

## 4. 研究问题草案

1. **技术—能力—行动**：LLM、地理邻近性增强 RAG、时空知识图谱与多模态数据，分别构成了哪些平台能力？这些能力中哪些在两处试点被实际使用，哪些仍停留在架构设计或展望？
2. **进入社区的组织过程**：研究团队、平台运营者、社区管理者与居民如何围绕 AskNearby 形成试用、内容供给、问答、反馈与治理行动？学术型社区与高密度混合社区的进入路径有何不同？
3. **使用与结果的证据边界**：论文报告的渗透率、活跃度、信息获取时间、人工咨询减少、工单响应、邻里互动等指标，分别对应什么对象、时间窗和基线？哪些是已实施行动，哪些只是作者报告的效果？
4. **社区治理角色**：平台在高校场景中主要改变个体适应与信息获取，在混合社区中是否承担“社会连接器”或治理中介角色？这一差异有哪些可核验证据与反证？
5. **试点与制度化边界**：AskNearby 是阶段性试点、常态化服务，还是仍在扩展中的技术原型？平台维护、数据更新、管理责任和后续评估是否有证据支持？

> 以上为草案；研究者可增删、改写或合并。未确认前不作为编码框架。

## 6. G0 已知的来源冲突与边界风险

1. **单一核心来源**：当前仅确认一篇论文作为核心材料；论文同时承担平台设计说明、试点记录和效果评估三种角色，尚无独立评估、平台日志或管理方材料互证。
2. **效果状态**：论文报告的数字与结论属于作者报道，不能直接写成“平台已经产生某因果效果”。G2 需区分“试运行已发生”与“效果被作者如此报告”。
3. **时间窗不一致**：高校场景明确写到 2024 年秋季入学与 30 天；南头古城未给出同样的起止日期。不得把高校的 30 天直接套用于南头古城。
4. **指标口径**：渗透率、活跃用户峰值、活动半径、信息获取耗时、人工咨询减少、工单响应提升、线下互动次数等指标的分母、基线、统计期和计算方法尚不完整，需逐条核对原文，不合并不同口径。
5. **对象身份**：“方元问问”是 APP/平台名称，`AskNearby` 是英文名；论文没有把“方元”定义为公司、社区或人物。不得因名称拆分出未经证据支持的独立主体。
6. **技术与能力**：架构图中的 RAG、知识图谱、多模态能力不等于两处试点均已使用；技术、能力、行动必须分开编码。
7. **试点与推广**：论文的“可扩展性”判断、A/B 测试、更多社区类型验证等，可能是设计主张或未来方向，不能写成已实施行动。
8. **案例编号**：既有图片台账已将 `C18` 分配给“方元问问（AskNearby）”；本案例沿用 C18，不改动 C01—C17 的编号与材料。
